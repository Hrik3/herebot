### Deep Overview

#### What the System Does
The system is designed to maintain an episodic memory, which stores sequences of experiences (episodes) that consist of states, actions, rewards, and next states. This memory serves as a reinforcement learning agent's repository for past interactions with its environment. The episodes stored in this memory are periodically sampled to train the agent offline, allowing it to learn from historical data.

#### Why It Exists
The primary motivation behind episodic memory is to enable an AI system to leverage historical experiences (episodes) to improve decision-making and performance in future tasks. Reinforcement learning agents can benefit significantly from being able to review past interactions with their environment, especially when such interactions are rare or costly. Offline consolidation through periodic sampling of episodes allows the agent to learn from previously gathered data without continuously interacting with its environment.

#### Conceptual Model Explained
The conceptual model is centered around episodic memory management and reinforcement learning:

- **Episodes**: Each episode represents a sequence of transitions (state, action, reward, next_state) that occurred during an interaction with the environment.
- **Capacity Constraint**: The number of episodes stored in memory is limited by a predefined capacity. This helps manage storage requirements and ensures that only relevant historical data influences future learning.
- **Offline Learning**: Periodic sampling from the episodic memory allows for offline training, where the agent can learn from past experiences without needing to continuously interact with its environment.

### Full Mechanism Breakdown

The internal workings of the system are detailed below:

1. **Initialization**:
    - The `EpisodicMemory` class is initialized either by default or based on a configuration provided through a `ConfigManager`. It sets up directories for storing episodes and loads existing ones.
  
2. **Episode Storage**:
    - When an episode (sequence of state-action-reward transitions) is generated, it gets appended to the list of stored episodes (`self.episodes`).
    - Each episode is saved as a JSON file in `EPISODE_DIR`.
    
3. **Capacity Management**:
    - If the number of stored episodes exceeds the predefined capacity, the oldest episode (first-in-first-out policy) is removed from memory and deleted from disk.

4. **Sampling for Offline Learning**:
    - Episodes are periodically sampled to train the agent offline.
    - The `sample_batch` method randomly selects a specified number of episodes from memory.

5. **Replay Sequence Generation**:
    - A sequential replay of stored episodes can be generated by calling `replay_sequence`.

2. **Sampling for Offline Learning**:
    - The sampling process involves selecting `n` episodes randomly with replacement if necessary,
     $$\begin{aligned}
        &\text{n} = \min(\text{n}, |\text{episodes}|) \\
        &\text{indices} \sim \mathcal{U}(0, |\text{episodes}|-1), \text{size=n}\\

3. **Replay Sequence**:
    A sequential replay returns the episodes in chronological order,
    $$
    \text{replay\_sequence()} = \text{self.episodes}
    $$

      - A random selection of episodes is performed without replacement.
      - The number of sampled episodes does not exceed the total number available.

### Limitations and Failure Modes

1. **When this approach breaks**: 
   - If the capacity is set too low, it may not retain enough historical data for effective offline learning.
   - The system relies on accurate timestamps in episodes; any drift in timestamps could result in incorrect episode ordering.

2. **Sensitivity to Parameters**:
   - The episodic memory's performance heavily depends on its capacity and configuration settings.
   - Changes in these parameters can significantly affect the amount of historical data available for learning.

3. **Trade-offs (accuracy vs compute, approximation limits)**:
   - A higher capacity improves accuracy by retaining more historical data but increases storage requirements and potential noise in training.
   - Lower capacity reduces storage needs but may limit offline learning effectiveness.
